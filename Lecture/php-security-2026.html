01 / FOUNDATIONPHP란 무엇인가?

PHP는 웹 서버에서 실행되며, 사용자 요청에 맞는 웹페이지나 데이터를 만들어 주는 프로그래밍 언어입니다. 로그인 확인, 게시판 글 저장, 쇼핑몰 주문 조회 같은 기능을 구현할 때 사용합니다.

쇼핑몰에서 ‘내 주문 내역’을 누르는 상황을 예로 들면 다음과 같습니다.

PHP 프로그램사용자 확인·처리
→

브라우저실행 결과 표시

브라우저가 받는 것은 PHP 코드 자체가 아니라 서버가 실행한 결과입니다. HTML이 페이지의 구조를 표현한다면, PHP는 서버에서 정보를 처리하고 응답을 생성하는 역할을 합니다.

PHP 프로그램과 PHP 엔진
개발자가 작성한 프로그램을 실제로 실행하는 소프트웨어가 PHP 엔진입니다. 이번 문제는 이 엔진 내부에서 발생했기 때문에, 사이트 코드나 플러그인만 바꾸는 것으로는 해결되지 않습니다.

02 / OVERVIEW어떤 보안 문제가 발견됐나?

원격 코드 실행(RCE)은 공격자가 네트워크를 통해 서버에서 자신이 원하는 코드를 실행하는 것입니다. 이번 문제는 조건이 맞으면 로그인 없이 악용할 수 있습니다.

점검 대상에는 Apache mod_php, PHP-FPM, php-cgi, FrankenPHP, LiteSpeed 등 웹 요청을 처리하는 PHP 환경이 포함됩니다. 실제 공격 조건과 성공 가능성은 환경마다 다릅니다.

03 / MECHANISM취약점은 어떤 원리로 작동하나?

① 작성하다 만 데이터를 정상 데이터로 처리

CVE-2026-109618은 PHP가 내부 데이터를 준비하는 도중 메모리 부족(OOM) 오류로 중단될 때 발생할 수 있습니다. 요청을 정리하는 과정에서 불완전한 데이터를 정상적인 것으로 취급하면 메모리가 손상됩니다.

내부 데이터 준비 → 메모리 부족으로 중단 → 불완전한 데이터로 정리 작업 → 메모리 손상 및 코드 실행 가능

Apache mod_php에서는 애플리케이션 코드가 실행되기 전 공격이 가능한 경로가 확인됐습니다. 웹사이트의 로그인 검사까지 도달하기 전에 문제가 생길 수 있습니다.

109618 기술 공지 ↗

② 이미 반납한 메모리의 주소를 계속 사용

CVE-2026-109619는 요청이 끝나고 메모리를 해제한 뒤에도, 이를 가리키는 내부 상태가 남는 문제입니다. 같은 작업 프로세스가 다음 요청에서 그 상태를 사용하면 이미 다른 용도로 바뀐 메모리에 접근할 수 있습니다.

이전 요청의 오류 → 메모리 해제·참조 정보 잔존 → 같은 프로세스가 다음 요청 처리 → 해제된 메모리 재사용

이를 Use-After-Free(해제 후 사용)라고 합니다. 공격 성립 여부는 요청 처리 경로, 설정, 확장 기능 등에 따라 달라집니다.

공격 시도와 침해 성공은 구분해야 합니다.
연구진의 성공 시연은 해당 제품을 사용하는 실제 운영 사이트의 피해를 뜻하지 않습니다. 공격 트래픽 관측만으로 데이터 유출이나 서버 장악이 성공했다고 단정할 수도 없습니다.

확인한 자료만으로는 특정 조직의 데이터 유출이나 대규모 침해가 확정됐다고 말하기 어렵습니다. ReliaQuest는 자사 발표 시점에 고객 환경에서 성공적인 악용을 관측하지 않았다고 밝혔습니다. 이는 모든 환경에서 피해가 없었다는 증거는 아닙니다.

공격 성공 시 코드는 웹 작업 프로세스의 계정 권한으로 실행됩니다. 그 계정이 접근할 수 있는 데이터가 위험해질 수 있지만, 자동으로 서버 관리자 권한을 얻는다는 의미는 아닙니다.

05 / REMEDIATION문제는 어떻게 해결했나?

PHP 개발팀은 엔진의 오류 처리와 내부 상태 정리 방식을 수정했습니다.

메모리 부족 처리 방식 변경

메모리 부족 때 처리 중인 문맥을 갑자기 벗어나던 방식을 변경했습니다. 안전한 실행 지점에서 오류를 처리하거나, 더 심각한 메모리 부족 시 프로세스를 종료하도록 하여 정리 과정에서 잘못된 상태를 사용하지 않도록 했습니다.

요청 사이에 남는 내부 상태 정리

요청에 속한 내부 상태가 다음 요청까지 남지 않도록 초기화·정리 처리를 보강했습니다. 해제된 메모리를 가리키는 상태가 후속 작업에 사용되는 원인을 제거하는 수정입니다.

각 계열에서 위 버전보다 이전 버전은 업데이트 대상입니다. 배포판이 수정 사항을 이전 버전에 반영했다면, 표시되는 버전 숫자와 함께 공급업체 보안 공지를 확인해야 합니다.

PHP 8.1 이하는 공식 지원이 종료됐습니다. 지원 버전으로 전환하거나 배포판·LTS 공급업체의 패치 제공 여부를 확인해야 합니다. 이번에는 예외적으로 7.4·8.0·8.1용 최소 소스 패치도 제공됐지만, 공식 지원 재개를 의미하지는 않습니다.

완전한 해결책은 PHP 보안 업데이트입니다.
웹 방화벽(WAF)과 설정 변경은 일부 공격 경로의 노출을 줄이는 보조 수단입니다. 사이트 코드나 플러그인 업데이트만으로 PHP 엔진의 취약점이 해결되지는 않습니다.
  1. 인터넷에 공개된 서비스부터 PHP 사용 여부와 실제 실행 버전을 확인합니다.
  2. 해당 환경의 보안 업데이트를 적용하고 실행 중인 서비스에도 반영됐는지 확인합니다.
  3. 호스팅을 사용한다면 제공업체에 PHP 패치 적용 여부를 확인합니다.
  4. 즉시 패치하기 어렵다면 외부 접근 제한이나 일시 중단을 검토합니다.
